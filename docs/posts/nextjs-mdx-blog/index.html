这个博客的架构：Next.js 16 + MDX 静态博客的工程实现

2026-07-06·3 min read
#Next.js#MDX#工程实践

这个博客没有用 Hugo 或 Hexo，而是自己用 Next.js + MDX 搭的。这篇文章讲清楚为什么这么做，以及核心的工程实现。

为什么不用现成的静态站点生成器

Hugo 快、Hexo 生态熟，但有两点让我选择了自建：

  1. 定制自由度：安全研究者的博客经常要贴代码、画表格、嵌工具输出，自建意味着排版规则完全由我控制——比如这篇文章里的终端风标题前缀，就是一行 CSS 的事
  2. 组件即内容：MDX 让文章里可以直接用 React 组件，写系列文章时可以抽可复用的展示组件

代价是要自己处理数据层和构建，但一个博客的数据层其实很简单。

数据层：文件系统即数据库

文章就是 src/content/posts/ 下的 MDX 文件，src/lib/posts.ts 负责读取和解析：

export function getPostBySlug(slug: string): Post {
  const fullPath = path.join(postsDirectory, `${slug}.mdx`);
  const fileContents = fs.readFileSync(fullPath, "utf8");
  const { data, content } = matter(fileContents);
  return {
    slug,
    content,
    title: data.title,
    date: data.date,
    tags: data.tags ?? [],
    // ...frontmatter 到 Post 对象的映射
  };
}

gray-matter 解析 frontmatter，剩下的就是纯函数式的过滤和排序。没有数据库、没有 API，git push 就是发布流程的全部。

一个踩过的坑：中文的阅读时长不能用空格分词计算。按每分钟 200 词算，一篇两千字的中文文章会得出 1 分钟——因为中文没有空格。正确做法是分开统计：

const cjkChars = content.match(/[\u3400-\u9fff]/g)?.length ?? 0;
const words = content
  .replace(/[\u3400-\u9fff]/g, " ")
  .trim()
  .split(/\s+/)
  .filter(Boolean).length;
const minutes = Math.ceil(cjkChars / 400 + words / 200);

MDX 渲染管线

文章页用 next-mdx-remote/rsc 在服务端渲染 MDX，rehype 插件链处理增强：

<MDXRemote
  source={post.content}
  options={{
    mdxOptions: {
      rehypePlugins: [rehypeSlug, rehypeHighlight],
    },
  }}
/>
  • rehype-slug：给标题生成锚点 id
  • rehype-highlight：代码块语法高亮，配合自定义的 highlight.js 配色

注意这两个插件必须显式传入，装了包不等于生效——这个博客一开始就只是装了插件没接管线，代码块是纯文本。

静态导出与部署

next.config.ts 三个关键配置：

const nextConfig: NextConfig = {
  output: "export",     // 静态导出，产出纯 HTML
  trailingSlash: true,  // /posts/xxx/ 形式，GitHub Pages 友好
  images: { unoptimized: true }, // 导出模式不支持默认图片优化
};

npm run build 产出 out/ 目录，GitHub Actions 把它复制到 docs/ 并推给 GitHub Pages。完整的部署细节（包括 trailingSlash 和相对路径的坑）单独写了一篇：Next.js 静态博客部署 GitHub Pages 的坑与解法。

值得吗

说实话，如果只是想写文章，Hugo 五分钟能上线。但如果你想要一个完全属于自己的排版系统、并且享受折腾的过程，自建的价值在于每一行 CSS 都是你写的——下次想改风格，改的是自己的代码，而不是别人的主题。
