TypeScript 工程实践：类型是文档，更是护栏

2026-06-20·3 min read
#TypeScript#工程实践

类型系统的价值不是给编译器看，而是给三个月后的自己看。这篇总结我写工具代码时反复用到的几个 TypeScript 实践，每一条都对应一个真实踩过的坑。

用 unknown 逼自己处理边界#

any 会传染——一个 any 进来，整条调用链的类型检查都失效了。解析外部输入（API 响应、配置文件、命令行输出）时用 unknown，编译器会强迫你在使用前收窄类型：

function parseToolOutput(raw: string): ScanResult {
  const data: unknown = JSON.parse(raw);
  if (isValidScanResult(data)) {
    return data; // 类型守卫通过后才有完整类型
  }
  throw new Error("unexpected tool output format");
}

JSON.parse 返回的永远是 any，先赋值给 unknown 变量再校验，这一步顺手就能把数据边界管起来。

可辨识联合：把非法状态消灭在编译期#

工具类代码最常见的是多状态流转。用枚举字符串字面量 + 开关式的接口建模，比一堆可选字段可靠得多：

type ScanState =
  | { status: "idle" }
  | { status: "running"; progress: number; current: string }
  | { status: "done"; findings: Finding[] }
  | { status: "error"; message: string };

function render(state: ScanState) {
  switch (state.status) {
    case "running":
      // 这里只有 progress 和 current，不可能访问 findings
      break;
    case "done":
      return state.findings;
  }
}

配合穷尽性检查，新增状态时编译器直接报错指出所有漏改的分支：

function assertNever(x: never): never {
  throw new Error("unhandled state: " + JSON.stringify(x));
}

satisfies：校验常量但不丢字面量类型#

配置对象（比如字典路径、目标分段）用 satisfies 校验结构，同时保留每个字面量的精确类型：

const config = {
  timeout: 5000,
  wordlist: "common.txt",
  threads: 32,
} satisfies Config;

// config.threads 依然是字面量类型 32，且拼错字段名直接报错

比 const config: Config = {...} 好在：类型注解会把对象"拓宽"成接口类型，satisfies 只检查不拓宽。

类型守卫：让判断逻辑只写一次#

function isFinding(x: unknown): x is Finding {
  return (
    typeof x === "object" &&
    x !== null &&
    "url" in x &&
    "status" in x
  );
}

把 x is T 的判断收敛成独立函数，所有需要校验的地方复用同一个实现。守卫函数写得越严，下游代码的空值处理就越少。

类型体操要适度#

最后泼一盆冷水：工具代码的目标是稳定和可读，不是炫技。条件类型、infer、递归类型这些用在库的公共 API 上值得，用在业务代码里只会让下一个改代码的人（包括你自己）痛苦。类型是护栏，不是迷宫。

我的判断标准：一个类型定义如果需要注释才能看懂，先想想是不是建模方式错了。
