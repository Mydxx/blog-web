传上去不算数：把文件上传当成一条流水线来测

2026-11-02·6 min read
#渗透测试#文件上传#工具开发#方法论

文件上传大概是 web 漏洞里辈分最高的一类，教程满天飞，payload 表格人人收藏。但真到项目里，我发现大部分人对它的理解停在"传个 shell 上去试试"。传上去了，报漏洞；传不上去，换下一个 payload。这件事的问题在于，上传成功本身什么都没证明。

最近读到一个 Go 写的开源扫描器 GoUpload，作者把文件上传拆成 13 个测试模块、344 个 payload，每个模块只回答一个问题：这条上传流水线里，到底是哪一层在做安全决策。我把它的研究文章和模块源码翻了一遍，这篇聊聊学到的细节，和我自己的看法。

同一个文件的三张脸#

先说一个我以前没这么明确过的模型：一个上传请求里的文件，其实同时拥有三种身份。

  • 扩展名，写在文件名里，给操作系统和中间件看
  • Content-Type，写在 multipart 头里，用户随手就能改
  • 魔数，文件开头那几个字节，给内容检测引擎看

正常用户的文件三张脸一致。攻击者的工作就是让三张脸互相矛盾，然后看哪一层先眨眼。比如一张真的 PHP 马，头上补六个字节 47 49 46 38 39 61，也就是 GIF89a，检测魔数的组件会把它认成图片，而 Apache 配了 AddHandler 的话照样按 PHP 执行。

三张脸都验完还有一个隐蔽战场：扩展名本身的写法。.php5、.phtml、.phar 是换马甲；.PhP 是赌过滤器大小写敏感、文件系统不敏感；.php.jpg 是赌 Apache 的 mod_mime 按多扩展解析。每一招骗的都是不同的组件。

**你测的从来不是"能不能传"，是"哪个组件在信哪张脸"。**这个模型一旦建立，payload 表格就不用背了，缺哪层测哪层。

Windows 文件名是个剧场#

文件名这一层的花活多到离谱，而且大多跟操作系统强绑定。几个我印象最深的：

  • shell.php. 和 shell.php （结尾带点或空格）：Windows 落盘时把结尾的点和空格剥掉，磁盘上躺的就是 shell.php。过滤器看到的是带尾巴的"安全"文件名，NTFS 给你存了个能执行的。
  • shell.php::$DATA：NTFS 交换数据流，IIS 会把它当主文件流处理。
  • 长文件名截断：255 字符的边界往后推，把正经的 .jpg 推出文件名，剩下的就是可执行后缀。
  • RTLO 反转符 \u202E：shell\u202Egpj.php 在界面上显示成 shellphp.jpg，骗的是看文件名的人。
  • 全角句号 ．（U+FF0E）：应用层按字符串比对认为不是点，文件系统做 Unicode 规范化之后它就是点。

这些招数的共同点：应用看到的字符串和文件系统最终落地的字符串，不是同一个。中间隔着 Unicode 规范化、系统截断、数据流处理，每一段都可能把"安全判断"和"安全后果"拆开。

Linux 下这些大部分失效，ext4 对文件名字面处理。所以这类 payload 是有明确目标画像的，见着 Windows/IIS 后端再上。

接收之后才是重点#

这是我读这篇研究最大的收获。以前我默认"传上去"就是终点，作者的模型把它画成一条流水线：校验通过，进存储，然后分流到下载、处理、解析、执行。同一个文件，落在这四个不同出口，风险完全不同。

  • 存了，但没人会去碰它：什么都不是，顶多算存储滥用
  • 公网可以直接访问：至少是个任意文件上传，能钓鱼挂黑页
  • 被当脚本解析：RCE
  • 交给下游组件解析：好戏才刚开始

下游解析才是宝藏区。传个 DOCX，里面 [Content_Types].xml 是 XML，可以塞外部实体读 /etc/passwd；传个 SVG，本身就是 XML，还能带外打云主机的 metadata 接口 169.254.169.254；传个压缩包，解压逻辑可能吃 ../../shell.php 这种 ZIP Slip；传个精心构造的 GIF+PHP 双格式 polyglot，图像校验和脚本执行同时骗过。甚至不用自己构造，传一个 .user.ini 写上 auto_prepend_file=shell.jpg，让整个目录的 PHP 请求都先包含你的"图片"。

所以结论是：**上传接口的校验做得再好，攻击面等于所有消费者的安全边界之和。**漏洞可以通过上传功能触发，但锅未必在上传校验头上。

200 OK 不算数#

这套扫描器另一个值得学的设计是结果分级。它不把"看起来有意思的响应"都标成漏洞，而是分五档：VULNERABLE、SUSPECT、SAFE、ERROR、UNKNOWN，判定前先跑一遍正常文件的 baseline，payload 的响应要和 baseline 对比才有意义。因为有的应用对一切上传都很客气，什么都能传，什么都有 200，这种"客气"单独看全是假阳性。

我特别认同这个思路。写扫描器的人容易掉进一个陷阱：payload 列表越攒越长，判定逻辑永远是"状态码 200 且响应里有文件路径就是洞"。这种工具在真实资产上跑一遍，出来的报告里十条有八条是废话，用两次就没人信了。扫描器之间的差距不在 payload 数量，在误报率，而误报率的解法不是更多规则，是把"证据强度"写进数据模型。

作者自己也划了边界：应用的文件处理意图、存储文件的业务影响、功能和安全边界的区别，这些他明确说自动化做不了。工具只负责把重复劳动压掉，把证据留给人。能说清楚"我什么不行"的工具，反而更值得信。

我自己的两点补充#

第一，实战里这套 13 层不用每次全跑。国内环境大量上传直接进 OSS 或云存储，"服务器解析"这条腿基本被砍掉了，三层以内就能下结论：随机改名加白名单后缀、存储和 Web 分离、图片重编码。这三招覆盖掉九成的点。剩下的硬骨头，才是逐层细测的战场。工具的价值在批量资产排查时的覆盖度，单点深挖还是得手工。

第二，这套"分层"思路不止管上传。接口参数校验、JWT 处理、消息队列消费，凡是"一个东西要流过好几道组件"的场景，都可以画同一条流水线，然后问同一个问题：**每道组件拿到的是信息的哪个版本，它又把自己的安全决策押在哪个版本上。**上传只是这条思路最经典的教学案例。
