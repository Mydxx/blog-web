做 Web 渗透和代码审计久了，会发现高危业务漏洞里占比最稳的永远不是炫技的内存破坏，而是**鉴权与授权边界的裂缝**。这类问题往往逻辑简单，却最容易在快速迭代里漏掉。这篇是我自己日常测试时顺手核对的一份精简清单。

## 一、先做最小闭环：去鉴权与身份切换

拿到一个核心业务接口（尤其是带 `id`、`uid`、`orderId`、`tenantId` 的写操作或查询接口），不要急着上复杂 payload，先跑三遍最小对比：

1. **剥离全部凭证重发**：去掉 `Cookie`、`Authorization`、自定义 `X-Token` 等头，看服务端是否真的返回 `401/403`，还是只靠前端路由守卫拦了一层。
2. **平级账号替换凭证（IDOR）**：保持请求路径和参数完全不变，只把凭证换成另一个同权限测试账号 B，用响应 Diff 直接看返回体里是否吐出了账号 A 的数据。
3. **降权账号调用管理接口**：把高权限接口路径直接拿普通用户凭证重放，确认后端是否存在「只校验已登录、未校验角色」的缺口。

## 二、Cookie 审计里最常被忽略的细节

看到响应头里的 `Set-Cookie`，除了常规扫一眼属性，重点看下面三处：

- **缺 `HttpOnly`**：一旦站点任意子模块存在反射型或存储型 XSS，会话凭证会被直接读走。
- **缺 `Secure`**：在混用 HTTP/HTTPS 或存在子域跳板的内网环境里，明文传输会直接暴露凭证。
- **`SameSite` 缺失或为 `None`**：敏感写操作若没有独立的 Anti-CSRF Token 或严格的 `Origin` 校验，就存在跨站请求伪造风险。

## 三、JWT 验签通过，不代表身份可信

之前在《签名是真的，用户是假的》里复盘过一个典型案例：很多系统把 JWT 当成银弹，以为调用了 `verify()` 就万事大吉。实战中至少要补查这四个边界：

```json
{
  "alg": "RS256",
  "iss": "https://auth.example.com",
  "aud": "billing-api",
  "sub": "u_10086",
  "exp": 1795500000
}
```

- **算法白名单**：服务端解码时必须显式锁定允许的算法列表，拒绝 `alg=none` 以及非对称公钥被误当成 HMAC 密钥的混淆攻击。
- **`iss` / `aud` / `tid` 绑定**：多租户或第三方 SSO 场景下，不校验受众（`aud`）与租户（`tid`）等于把别家系统的合法令牌当成自家通行证。
- **吊销与过期窗口**：纯无状态 JWT 在用户修改密码、被管理员踢下线后，如果服务端没有版本号（`tokenVersion`）或短生命周期 + Refresh 机制，旧令牌在 `exp` 前依然畅通无阻。
- **不要把敏感字段明文塞进 Payload**：JWT 默认只是 Base64URL 编码，不是加密；手机号、内部角色标志或调试开关放在 Payload 里等于公开广播。

## 四、别被「前端状态字段」骗了

测试登录态、会员权限或审批流程时，经常会遇到前端根据 `/api/auth/status` 返回的 `{"isLogin": false, "role": "guest"}` 来决定渲染哪些按钮和菜单。

用响应替换把前端状态强行改成 `true` 或 `admin` 后，**真正有价值的不是「页面把管理菜单渲染出来了」**，而是顺着暴露出来的菜单去触发背后的真实写接口，验证服务端是否同样做了权限兜底。前端拦不住人，服务端守住才算数。
