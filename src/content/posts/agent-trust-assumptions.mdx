前阵子翻 A2A 协议相关的资料，越翻越觉得眼熟。倒不是看到了什么石破天惊的新攻击，而是那种"这个坑我见过"的感觉越来越强——只是这一回，坑不是开发者自己挖的，是框架替他们挖好的，还配了教程。

## 名字从来不是身份

A2A 里每个 Agent 有一张 AgentCard，上面有名字、能力描述、端点。名字这个字段，设计初衷是给人看的。但你去翻各种示例代码，几乎都能找到这样的写法：

```python
routes = {}
routes[card.name] = client  # 先到先得，重名时看谁后到
```

"看谁后到"这五个字就是全部漏洞。两个对端重名时，查找取先到的、或者后写的把先写的覆盖掉、broker 把两者折叠到同一条路由——总之，发给受信任 Agent 的任务，从某一刻起悄悄改道到了另一个对端。任务里带着什么？提示词、上下文、会话状态，运气差一点还有委派凭证。

这不是 A2A 特有的病。包管理器的 typosquatting、内网里拿主机名做鉴权判定的祖传系统、早年 JWT 对签发者字段的处理，全是同一个病根：**把给人看的标识符，当成了给机器做决策的键**。

为什么这个坑一犯再犯？我自己的观察是，名字当 key 太顺手了。字典的 key 要什么？要可读、可 debug、日志里肉眼可查。稳定 ID 呢？一串 UUID，毫无感情。于是示例代码用名字，demo 流传成教程，教程流进生产。

规范层面还有一层更微妙的东西。A2A 规范并没有说"你必须按名字路由"，所以严格讲这是实现缺陷，怪不到协议头上——话是没错。但规范要求名字必填、却不提供稳定标识符和冲突语义，等于把最要命的安全决策留给每个实现者自由发挥。而生态不会自己发明安全的做法，生态只会收敛到最省事的写法。OAuth 早年的实现偏差，JWT 的 alg 参数被玩出的花样，都是同一个剧本：**规范没规定死的地方，就是未来漏洞的集散地**。

所以我的立场很简单：名字只进 UI，路由、鉴权、工具注册全走稳定 ID，而且 ID 必须绑定到可信来源——自己声明的 ID 照样能被抄。重名怎么办？报错。fail-closed，绝不挑一个胜者。

## 批准不是授权

第二个想当然更隐蔽，因为它伪装成"更安全"的设计：敏感操作前加一道人工审批。

问题在于，审批的意义从来不是"有人点了同意"这个动作，而是**点同意的人看到的东西，和系统接下来执行的东西，是同一个**。这两者之间只要存在时间差和可变状态，审批就退化成一次 TOCTOU 检查——check 在 t0，use 在 t1，中间谁能动状态，谁就握着真正的授权。

拆过几种实现之后（不点名了，文末有出处），坏味道集中在两类。一类是审批界面只给你看一半：比如一条 shell 命令，界面上渲染的是命令本体，位置参数、环境变量、重定向这些统统不展示——你以为批的是 A，请求里早就装着 B 的全部材料，点完同意 B 就上路了。另一类更工程化：批准和执行之间隔着持久化状态，pending 的待审内容可以被另一个有写权限的角色替换掉，而恢复流程只核对"这个任务批过没有"，从不核对"现在要跑的，还是你批的那个吗"。

银行早就把这个道理讲透了：转账确认页必须显示完整卡号、户名、金额，一个字都不能省——因为银行知道"确认"必须绑定到精确对象上，绑定不了就是事故。工程上做对的样本也有：有的 SDK 把批准记录做成一条 canonical 数据，完整工具名、全部参数、目标资源、发起者、内容摘要，跨序列化和恢复全程携带，恢复时逐字比对，对不上直接抛异常。**批准从"一个按钮"变成"一条数据"，才算得上闸门。**

## 为什么 Agent 时代会集中爆发

说实话，这两个问题单拎出来都不新，安全行业为它们交过的学费摞起来比我高。值得写一篇的原因是 Agent 工作流这个生态位自带三个放大器。

一是实现同质化。interrupt/resume 这套人审范式被框架们互相抄，示范工程长一个样——于是一个坑被批量复制进所有照着模板起步的平台，修一个等于要修一个时代。

二是授权粒度的退化。Agent 场景里"会话"和"任务"的边界比 Web 模糊得多，开发者下意识把授权挂在会话或任务 ID 上。我之前拆解 AI pentest Agent 的时候写过一条结论，这里再放一遍：授权必须绑定到不可变的具体对象上，任何会话级、名字级的授权，都会被时序拆开。

三是审批疲劳。人审一旦高频出现，就会滑向肌肉记忆式点击。闸门还在，人已经不在了——攻击者甚至不需要绕过它，等你自己点。

冷静剂也要给足：这一轮公开研究用的多是刻意挑选的样本，不少攻击路径是条件性成立，远不是"所有 Agent 平台已被通杀"。但模式级缺陷从来不看个案，它只在乎有多少新系统正在照着同一个模板盖楼。

## 两张自查清单

给写 Agent 平台的人：

- 路由、注册、工具命名全部走稳定 ID，名字只进 UI
- ID 绑定可信来源；自报家门的 ID 默认不可信
- 重名 fail-closed，规范化等价（大小写、空白、Unicode）也算重名
- 审批记录是一条数据：完整工具名、全部参数、目标资源、发起者、内容摘要、时效与消费状态
- 恢复执行时与批准记录逐字比对，原子消费防重放
- 待审状态对非审批者只读

给做审计的人，两条不变量值得一测：

- 重名测试：用不同来源注册同名对端（记得带上规范化变体），然后追最终连接落点——注册成功、返回 200 都不证明绑定正确
- 换水测试：走完"展示 A、批准 A"之后，在执行前把待审内容换成 B（保持任务 ID 不变），看系统拒不拒

## 写在最后

Agent 系统没有发明新的信任问题。名字和批准这两个词，在安全语境里从来都不是承诺——一个是展示，一个是时点。把展示当身份、把时点当授权，是每一代新架构都要重交的学费。Agent 只是让这份学费，看起来格外贵了一点。
